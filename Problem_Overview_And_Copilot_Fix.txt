Yes — this confirms the problem.

Your HR Agent itself is enforcing the “draft → human approval → send” behavior, rather than Gmail MCP requiring that behavior.

So even if Gmail MCP has a working send_email tool, your current architecture is effectively:

User → HR Agent → send_email → create draft → Side Canvas → approval → /api/chat/confirm → actually send

instead of:

User → HR Agent → Gmail MCP send_email → Gmail sends

The important distinction

There are really two separate layers:

MCP layer
Gmail MCP exposes tools such as reading/searching/sending email.
It should be capable of performing the actual action.
HR Agent orchestration layer
Your route.ts / hr-actions.ts is deciding that sending email is a risky action.
It converts the action into an approval artifact.
ConfirmRisky then requires the user to approve it.

So adding/fixing Gmail MCP won't automatically remove the approval requirement.

What I'd change

If your goal is a production HR agent that can actually execute workflows autonomously, I would not remove human approval globally.

Instead, make the policy tool/action-specific and configurable:

Read operations → automatic
Low-risk writes → automatic if configured
External communications → configurable
High-risk HR actions → always require approval
Unknown/destructive actions → always require approval

For example:

Action	Default
Search Gmail	Auto
Read email	Auto
Create email draft	Auto
Send routine email	Configurable
Send termination email	Approval
Change employee compensation	Approval
Delete HR data	Approval
Send Slack message	Configurable

The biggest architectural issue is that your code currently appears to have specific knowledge of send_email, send_slack_message, and send_teams_message. That means the agent/orchestrator is treating these as special HR workflows rather than simply discovering and executing MCP tools according to a general policy.

What you should tell Claude

I would have Claude refactor it so that the MCP server owns the actual tool implementation, while the HR Agent owns a generic permission/approval policy.

In other words:

Don't hard-code “email = draft only” into hr-actions.ts.

Instead:

Look at the MCP tool's metadata/policy and determine whether approval is required before executing it.

That will make your architecture much more scalable when you add Gmail, Slack, Teams, GitHub, Linear, Microsoft 365, etc.

And importantly, keep the approval infrastructure. Just stop hard-coding every communication tool into “draft only.”
